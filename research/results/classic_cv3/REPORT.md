# 经典 CV v3：远距/小光斑检测（A–F 计划执行报告）

## 0. 一句话结论

真实手机取景（4:2:0 色度 + ISP 降噪 + 曝光衰减 + 模糊）下，v2 的**绝对亮度阈值**在远距失效：同一批 12 条 hard_test 序列，clean 时 classic2 det@10 all 0.815，phone_far 掉到约 0.36。v3 把前端换成**颜色差 + 形态学顶帽的局部对比度**（阈值由高频 MAD 噪声自适应决定，去掉了绝对亮度门），用上一帧追踪位姿推出光斑像素半径做**尺度自适应**的核与窗口，对 1–3px 小点做 **ROI ×4 上采样亚像素质心**，并在某色候选缺失时用**亮度对比度候选 + 颜色合理性否决**兜底。结果（12 序列同帧同解码对照）：phone_far 上 det@10 all 从 classic2 的 0.340 提到 **0.777**，phone_easy 从 0.361 提到 0.814，干净集不降反升（0.824 vs 0.815）；代价是每帧耗时约 78ms（纯对比度）→151ms（并集），App 端需要降分辨率/金字塔才能上机。另外在 App 采集侧（E）加了高分辨率分析 / 关闭 ISP 降噪 / 锁定白平衡三个开关；并用退化模型做了开关归因（§4.2）：**色度 4:2:0 下采样是远距失效的头号外因**（只恢复 4:4:4，classic2 0.367→0.659、v3 0.656→0.746），而单纯提高分析分辨率对经典前端反而更差（classic2 0.367→0.324；v3 持平），只有和 4:4:4 色度一起上才有收益（v3 0.656→**0.794**，小点桶 0.292→0.600）；关 ISP 降噪与 JPEG=100 在合成模型里是负收益（§4.3）。在唯一一条真实视频（近景桌面、无标注）上做内容级验证：把它退化到三档后，classic2 仍「检出三点」但点漂移 260–318px（锁到干扰块上、视边长 152→414–473px 的假三角形），v3 同条件点漂移 0.37–1.08px。

## 1. 诊断：远距为什么会失效

合成 hard_test 中 `edge_px ≈ fx·L/depth`：fx≈1108、L=100mm ⇒ 1m 111px、3m 37px、5m 22px、10m 11px；点半径约 0.09·edge_px，5m 时 2–3px、10m 时 1–2px。

App 侧 `BrightSpotDetector.kt` 用绝对亮度阀门（`minPixelBrightness=10`、`minTotalBrightness=20`、`dynThreshold=max(30, 0.7·maxBrightness)`、`minRefineRadius=2`）：小点被 4:2:0 色度下采样抹成灰色、被 ISP 降噪抹掉高光、AE 拉低曝光后整体亮度不足 ⇒ 在阈值前就消失。

离线分桶（classic2、全分辨率、hard_test 全可见帧，按 GT 视边长）：<64px 0.511 (n=176)、64–100px 0.676 (n=657)、≥100px 0.746 (n=1694)；漏检归因：153 帧有候选但拼错、576 帧前端就没有候选。

## 2. 退化模型与评测口径（F）

`research/tridot_temporal/degrade.py` 按真实成像链路建模：光学（离焦）→ 传感器（降采样、曝光增益/偏移、散粒+读出噪声、4:2:0 色度往返）→ ISP（中值降噪、锐化、JPEG）。随机项按 `(preset, frame_index)` 确定性播种。四个 preset：`clean` / `phone_easy` / `phone_far` / `phone_harsh`；9 个单测覆盖恒等、确定性、色度保亮度、降采样降峰、降噪抹 1px、JPEG=100 恒等。

评测口径沿用 `eval_v2`：det@10 all（分母=全部帧，遮挡帧算失败）、逐点 recall@10、pose coverage、t_err 中位/p90、延迟；`far_bench.py` 再按 GT 视边长分桶。所有数字都来自同一解码、同一 PnP、无任何在线门控或后处理手调。

## 3. 实现（A–D）

* **A 局部对比度前端**：颜色差图 `clip(channel − max(others))` → 形态学顶帽（`MORPH_TOPHAT`，核由 B 给出）→ 阈值 `thr = max(contrast_floor, k_sigma·σ_noise, rel_frac·p99.5)`，`σ_noise = 1.4826·MAD`；绝对亮度门全部去掉。
* **B 尺度自适应**：`r_px ≈ 0.09·edge_px`（上一帧追踪位姿给出），顶帽核 `2·(2r)+1`（≤31），精修窗口 1.5–2×r_px、同色去重半径随 r 缩放；无位姿时退化为多尺度 (3,7,15,31) 取最大响应。
* **C 小点亚像素**：连通域 <4px 时，在周围取 patch 双三次 ×4 上采样，在上采样后的颜色差图上做加权质心。
* **D 检测-颜色解耦**：某颜色候选为空时，用亮度对比度候选补位，并用其它两色 map 的强度做「颜色合理性」否决（≥40 且 ≥1.6×自身强度 ⇒ 该点属于别的颜色）。

### 4.1 端侧 A–D：`FarSpotDetector`（远距回退检测）

只做采集侧不够：手机上真正跑的还是 `BrightSpotDetector` 的绝对亮度阈值 + 光斑连通域，远距离 1–2px 的点根本进不了候选。所以把 A–D 的前端精简成纯 Kotlin 落地（App 里没有 OpenCV）：

- `composeApp/src/androidMain/kotlin/org/example/tridotpnp/FarSpotDetector.kt`
  - 颜色差图 `r−max(g,b)` / `g−max(r,b)` / `b−max(r,g)`（与 Python `classic_v3.color_weight_maps` 同一权重定义）；
  - 形态学顶帽去背景：`response = map − opening(map, k)`，`min/max` 滤波用**单调队列**实现，O(1)/像素，核可以开到 31 而不变慢；
  - `k` 由上一帧位姿估的光斑半径推（`r ≈ 0.09·edge_px`，即研究里 0.087 的实测比），没有位姿时退化成 3/7/15/31 多尺度取最大（B）；
  - 阈值 = `max(floor=12, 3.5·σ_MAD, 0.18·p99.5)`，没有绝对亮度门（A）；
  - 8 连通域 + 响应加权质心；`area ≤ 3` 的连通域再用双三次 ×4 上采样求质心（C）；
  - 三点还要过等边校验（平均边长 ≥6px、最长/最短 ≤1.6、面积 ≥0.08·mean²），宁缺毋滥；
  - 某色完全缺失时（YUV 4:2:0 把 1–2px 彩点平均成灰白是真实手机的头号失效模式），用亮度顶帽找候选，再由「该处没有其它颜色的强证据」（其它色差 <40 或 <1.6×本人）决定是否给缺失颜色补位（D）。
- 接线：`CameraFrameProcessing.processImage` 在 `refineSpotsOnOriginal` 之后，如果 `refinedSpots.size != 3 && tuning.farDotAssistEnabled`，就在全分辨率 `rotatedBitmap` 上跑一次回退检测（内部自己缩到 640 长边），成功则替换三点；`App.kt` 的「采集与远距」段加了开关（默认开）。
- 证据：`composeApp/src/androidUnitTest/.../FarSpotDetectorTest.kt` 9 个测试（JVM，合成 IntArray）与 `FarSpotFixturesTest`（真实帧固件）：1–2px 点定位 <1.5px、加性噪声下仍检出、40×40 白色大块不误检、缺色返回 null、共线三点被几何校验拒掉、`expectedEdgePx=300` 时 31 核仍能找到 1px 点、色度强度可分、640×360 多尺度平均耗时 **74.9ms**（早期版本 181.7ms；按尺度从小到大尝试、凑齐三色即停）；`testDebugUnitTest` **21 个测试全过**，`assembleDebug` 成功（APK 68,816,419 B，dex 含 `FarSpotDetector` / `farDotAssist` / `farDotAssistEnabled`）。
- 2026-10-29 追加（round 3）：
  - 选点从「每色取 top1 + 等边几何校验」改成**穷举三元组打分**（`pickTriangle`）：约束 meanEdge ≥6px、有 `expectedEdgePx` 时 `meanEdge/expected ∈ [0.6, 1.7]` 且面积 ≥0.08·mean²，代价 `shape + 0.5·|log(meanEdge/expected)| − 2.4·phot + 0.8·时序偏离`，`cost ≤ 2.2` 才接受。没有硬时序门限——真实帧上硬门限会直接无解。
  - 候选从「对比度顶帽」扩成 **union**：每色再并入「原始颜色差图 + 绝对阈值 `max(12, 0.22·p99.5)`」的候选（与 Python `classic_v3` 的 union 同一动机：饱和点/强泛光下顶帽会削掉光斑核心）。
  - 预测先验：`detect(bitmap, expectedEdgePx, predictedSpots)` 接收上一帧三点（`lastTriSpots`），用于尺度选择与打分中的时序项。
  - 真实帧固件：`research/scripts/make_far_fixtures.py` 从 `hard_test` 导出 4 factor × 2 preset = 8 张 640 宽 PPM（附 GT 与「上一帧 GT」预测），`FarSpotFixturesTest` 做契约断言 + 窗口精度断言。结果（honest）：
    - `syn_far_0228` clean 最坏点误差 **0.97px**、`syn_handheld_0218` clean **0.96px**（1–2px 孤立点可检）；
    - `syn_clutter_0209` clean/phone_far → **null**（杂波候选压过目标，宁可不出）；`syn_screen_0212` clean 选错 **110px**；4 张 phone_far **全 null**（2× 降采样 + 4:2:0 后 640 分辨率下色度响应已不可靠）。
  - 结论：单帧 + 640 分辨率的前端只在「孤立小点」窗口成立；杂波/屏幕泛光/强退化场景需要多帧时序关联（用追踪位姿做候选-角点匹配）或更高分析分辨率。
- 2026-10-29 追加（round 4，位姿校验选择器）：
  - **候选层面**：连通域阈值法在大块杂波里会把目标点和背景连成一片，导致真正的点被面积过滤掉（clutter 帧里 GT 绿点峰值只有 12–45，却和上百像素的杂波同属一个连通域）。改成**局部极大 + 阈值**（`response ≥ max(floor, 3.5σ_MAD, 0.18·p99.5)` 且 `response == 5×5/9×9 邻域最大值`），大幅块内的每个小峰都会被单独取出；`topKPerColor` 5→12，去重半径 20→10px。
  - **选择层面**：透视下投影三角形本来就不是等边，几何硬门限必然误杀。改成「每色候选 + 上一帧预测门限 `max(12px, 0.45·edge_px)` + PnP 位姿校验」：候选三元组解 P3P，用 `PnPTemporalTracker.posesForTriple` 遍历全部几何根，只接受「平移 ≤ `max(150mm, 0.25·depth)` 且旋转角 ≤25°」的根，取代价最小者；代价 = `0.5·shape + 0.5·|log(mean/expected)| + 0.6·时序偏离/3 + 0.5·位姿代价`，无 phot 项（透视下亮度不可靠）。
  - **解算层面（真 bug）**：`solveDepths` 原来只有「残差 ≤0.05mm 才算收敛，否则 50 轮后返回 null」。真实检测有 1–2px 像素噪声，三条边不可能同时精确等于 100mm，结果几乎全部无解。改成「记录残差最小的解，残差 ≤2mm 即接受」，噪声帧也能给出稳定根。
  - **证据（8 张真实帧固件，640×360，带上一帧位姿先验）**：`syn_clutter_0209` clean **3.36px**、phone_far **3.36px**；`syn_far_0228` clean **2.46px**、phone_far **1.17px**；`syn_handheld_0218` clean **2.30px**、phone_far **0.89px**；`syn_screen_0212` clean/phone_far 前端**根本看不到点**（GT 处颜色差只有 5–16，最近候选 43–112px）→ 返回 null（honest miss）。准确率 **6/8**，除 screen 外全部 <8px（round 3 是 1/8）。
  - Kotlin 单测 **23 个全过**（11 tracker + 9 detector + 3 fixtures）；APK 68,825,423 B（dex 含 `posesForTriple`/`buildFarTripleValidator`/`TripleValidator`/`seedState`）。

## 4.2 采集侧开关 A/B（用退化模型替代真机）

手机端能改的不只是算法：分析分辨率、色度格式、ISP 降噪、JPEG 质量都会改变输入统计。为了给 E 一个**量化**依据（真机还拿不到），在 `phone_far` 退化上逐个关掉一种退化（`hard_test` 前 6 序列、`classic2` = 绝对阈值前端 ≈ App 现状；`classic3_union` = 对比度并集前端）：

| 配置（相对 phone_far） | classic2 det@10 all | 40–80px | 80+px | 80+px t_err 中位 |
| --- | --- | --- | --- | --- |
| baseline | 0.367 | 0.108 | 0.402 | 8.9 mm |
| 只关 JPEG（quality 100） | 0.417 | 0.138 | 0.455 | 7.6 mm |
| 只关 ISP 降噪 | 0.389 | 0.108 | 0.427 | 9.2 mm |
| 只用 4:4:4（不做色度下采样） | **0.659** | 0.108 | **0.735** | 6.5 mm |
| 只关传感器降采样（分辨率翻倍） | 0.324 | 0.077 | 0.358 | 7.3 mm |
| 全开（上述全关） | 0.524 | 0.123 | 0.579 | 6.9 mm |

（`classic3_union` 同条件：baseline 0.656 / **chroma 4:4:4 0.746（40–80px 桶 0.292 → 0.569，小点收益最大）** / 全开 0.452。）

结论：

1. **色度 4:2:0 是远距失效的头号外因**：只把色度恢复成全分辨率，绝对阈值前端就从 0.367 → 0.659（+0.29，接近翻倍）；JPEG 质量 +0.05、ISP 降噪 +0.02 属次要。
2. **分辨率单独提高反而变差**（classic2 0.367 → 0.324；v3 0.656 → 0.667，几乎不变）：去掉传感器降采样等于同时去掉其平均噪声的效应，高频噪声增多，候选变脏。§4.3 的阈值对照表明这**不是**「分位数阈值被内容抬高」造成的（实测有效阈值一直停在常数底 12），见 §4.3。
3. **「全开」不是最优**（0.524 < 0.659）：关降采样 + 关降噪带来的噪声/杂波抵消了色度收益。E 的推荐组合应优先「色度质量（避免二次压缩、尽量拿高质量 YUV/RGB 流）」与「适度降噪」，而不是盲目拉高分辨率。
4. 合成退化只能模拟到传感器/ISP 的统计层：真机的去马赛克、卷帘、AE/AWB 漂移不在模型里，因此这张表的**方向可信、幅度不可当承诺**；真机到位后按 `research/docs/real_device_protocol.md` 复测。

### 4.3 阈值模式对照与更细的采集归因（round 6）

**问题**：§4.2 曾推测「更清晰/更噪的帧把 `max(12, 3.5σ_MAD, 0.18·p99.5)` 抬高 → 漏检」。若成立，把阈值换成「不受内容锐度影响」的估计（分块 MAD 的 p25 作噪声底）应该让采集收益回来。为此给 `ClassicV3Detector` 加了 `threshold_mode ∈ {percentile, tile, tile_rel, snr}` 并用 `research/scripts/threshold_ab.py` 在同一批帧上对照（`hard_test` 前 6 序列、四配置、同解码）：

| 配置 | classic2 | v3 percentile | v3 tile | v3 tile_rel | v3 snr |
| --- | --- | --- | --- | --- | --- |
| clean | 0.743 | 0.750 | 0.746 | 0.750 | — |
| phone_far | 0.367 | 0.656 | 0.656 | 0.656 | — |
| highres（只去降采样） | 0.324 | 0.667 | 0.667 | 0.667 | 0.548 |
| all_on（全关退化） | 0.524 | 0.452 | 0.452 | 0.452 | 0.209 |

**结论 1：阈值模式在这里完全不影响结果，原假设被证伪。** 直接测量（2 序列 × 6 帧 × 四配置）显示：`σ_MAD` 与分块 `σ` 中位数都是 **0.00**，`p99.5` 中位 28–39 ⇒ `0.18·p99.5 ≈ 5–7 < 12`，三种模式的有效阈值都停在常数底 **12**。所以问题不在「阈值被锐度绑架」，v3 的所谓「局部对比度」在这些帧上实际退化成「绝对对比度 > 12」。`snr` 模式（逐像素噪声归一化）明显更差：它在光斑自身与杂波上高估噪声、把真点也一并压掉（highres 0.667→0.548、all_on 0.452→0.209）。

**结论 2：把「更细归因」补上后，采集侧的真实故事是「色度第一、噪声第二，两者要一起管」。** 追加跑 `highres+4:4:4` 与 `highres+4:4:4+关降噪`（同 6 序列、v3 并集与 classic2 同表）：

| 配置 | classic2 | v3 并集 | 40–80px（v3） | 80+px（v3） |
| --- | --- | --- | --- | --- |
| baseline（phone_far） | 0.367 | 0.656 | 0.292 | 0.705 |
| highres+4:4:4 | 0.672 | **0.794** | **0.600** | **0.821** |
| highres+4:4:4+关 ISP 降噪 | 0.578 | 0.778 | 0.569 | 0.806 |
| all_on（再加 JPEG 100） | 0.524 | 0.452 | 0.277 | 0.476 |

- **色度 4:4:4 仍是最大单项**（v2 +0.29、v3 +0.09），且分辨率只有和 4:4:4 一起上才有效：`highres` 单独 v2 −0.04、v3 +0.01；`highres+4:4:4` 才把 v3 推到 0.794（小点桶 0.292→0.600）。
- **关 ISP 降噪是有代价的**（v3 0.794→0.778；classic2 0.672→0.578，小点桶 0.154→0.015）：噪声会生成假候选，前端阈值不是唯一防线。
- **JPEG quality=100 不是「更好」**：它不再对色度做平滑（等效去掉一道噪声抑制），叠加后 v3 掉到 0.452。合成退化里的「全开」等价于「把所有噪声抑制都拿掉」，不是真机上的更优配置。
- 因此 E 的建议顺序应改为：**优先拿 4:4:4 色度（避免二次 4:2:0 压缩）→ 保留适度 ISP 降噪 → 再谈提高分辨率**；「关降噪/拉高分辨率」本身不是目标。

**局限（新增）**：这张表只说明「在本文的退化模型里哪些环节最值钱」，不能反推真机的 ISP 行为；真机数据到位后按 `research/docs/real_device_protocol.md` 复测，并且应该把「4:4:4 色度流/1920×1080 分析/降噪等级」作为三个独立自变量分别扫。

### 4.4 候选级时序门控（prune）是负结果（round 7）

§4.3 的结论是「限制在候选质量/选点，而不是阈值」，于是最后试了最直接的候选层改动：用上一帧位姿预测三色像素（`_predict_pixels`，误差 ~1–2px 量级），把距预测点超过 `0.55·edge_px` 的候选**先剪掉**再做三元组搜索（`prior_gate`，剪枝后无解时回退全量）。四配置 6 序列、同帧同解码：

| 配置 | v3_union | +prior_gate（prune） | 差 |
| --- | --- | --- | --- |
| clean | 0.750 | 0.720 | −0.030 |
| phone_far | 0.656 | 0.607 | −0.049 |
| highres_chroma | 0.794 | 0.780 | −0.014 |
| all_on | 0.452 | 0.411 | −0.041 |

三种变体（只对主搜索剪枝、放宽门限 0.8、以及「剪枝结果与全量结果按代价取优」的 dual 模式）在 3 序列上复核（phone_far / all_on）：

| 配置 | base | prune | dual |
| --- | --- | --- | --- |
| phone_far | 0.656 | 0.656 | 0.656 |
| all_on | 0.478 | 0.367 | 0.478 |

**结论**：候选剪枝不但没有收益，还会掉 0.01–0.05；`dual`（剪枝只作为另一条候选路径，按总代价择优）能消除掉点但也**没有收益**。原因：三色选择本来就是「对上一帧位姿的软一致性」（`_score_triple` 里已有 0.8·时序项），剪枝只是把软约束变成硬约束——在遮挡/漏检后追踪位姿本身有偏差时，硬约束会先把真点剪掉；而在预测较准时，软项已经足够选出同一组。另一个证据是：`clean`（位姿最准）也掉 0.03，说明掉点主要不是「预测漂移」，而是**候选多样性被砍掉后，代价函数更容易锁到「离预测近但错」的三元组**。

**上机含义**：App 端 `FarSpotDetector.pickTriangle` 原来对候选做 `0.45·expectedEdgePx` 的硬关联门限，属于本轮被证伪的「prune」语义。已改为**两遍搜索**：第一遍带门限（快速路径），第一遍没有可接受三元组时第二遍在**全量候选**上重搜（`scanTriples(applyGate=false)`），即「门限只做加速/去噪，不做否决」。Kotlin 单测与固件测试同步通过。

### 4.5 2 点 + 已知几何（round 8）：数学可行，瓶颈在前端与先验启动

动机：`det@10 all` 把「GT 少于 3 点可见」的帧一律记失败，而 hard_test 里恰好 2 点可见的帧有 **655** 帧（hardmix 400、occlude_hand 134、handheld 63、screen 26、room 17、crosscolor 15；occlude_hand 更是 0 帧三点全可见）。已知靶标几何（等边 100mm），理论上两点 + 先验就能定姿，比「补第三点再 3 点 PnP」更稳。

实现（`research/tridot_temporal/pnp2.py`）：

- `solve_pose_2point(uv, obj, K, R_prior, t_prior, ...)`：6 维未知量（绕先验的旋转向量 + 平移），残差 = 2 点重投影（σ=1.5px）+ 平移先验（σ=300mm）+ 旋转先验（σ=0.2rad）；LM + 分块步长；接受条件重投影 ≤3px、旋转跳变 ≤25°、平移跳变 ≤max(250mm, 0.35·depth)。
- `solve_pose_2point_plane(...)`：不用历史，只用「靶标平面大致正对相机」的先验（重投影 + 法向残差），探索无先验帧的可行性。
- 5 个单测（精确/噪声先验、坏先验拒绝、点数校验、重投影一致性）。

评测（`research/scripts/two_point_ab.py`，同帧同检测/解码，655 帧）：

| 方法 | coverage | t_err 中位 | t_err p90 | ≤50mm |
| --- | --- | --- | --- | --- |
| `current`（现有 3 点管线） | 0.953 | **574mm** | — | — |
| `completion`（先验投出缺点） | 0.438 | 601mm | — | — |
| `two_point`（top-1 候选） | 0.144 | 26.8mm | 805 | — |
| `near`（预测点最近候选 + 门限） | 0.144 | 222.6mm | — | — |
| `checked`（near + 缺失点处无该色证据） | 0.136 | 220.6mm | — | 0.39 |
| `oracle`（GT 像素，上界） | 0.162 | **20.6mm** | 46 | 0.91 |

`current` 的中位误差 574mm / 旋转 132.6° 说明：现有管线在这些帧上**不是没输出，而是给出了自信的错位姿**（补了假第三点）。分因子看，方法只在两点本身可靠时才有意义：

| factor | 帧数 | prior 可用率 | `checked` cov / t_med | 备注 |
| --- | --- | --- | --- | --- |
| crosscolor | 15 | 1.00 | **0.93 / 3.6mm** | 两点清晰可见 |
| room | 17 | 1.00 | **0.88 / 21.2mm** | 同上 |
| screen | 26 | 1.00 | 0.31 / 238mm | 前端看不到点 |
| handheld | 63 | 0.94 | 0.16 / — | 运动模糊 |
| hardmix | 400 | 0.43 | 0.10 / 734mm | 先验陈旧 + 前端漏检 |
| occlude_hand | 134 | **0.00** | **0.00** | 无任何三点全可见帧，跟踪无法启动 |

hardmix + occlude_hand 合计 534 帧的专项诊断：先验可用率 0.318、**先验年龄中位 15.5 帧**（p90 28）、被观测两点相对 GT 的**检测误差中位 325px**；`oracle`（直接给 GT 像素）只通过 2.8%（多数被 25° 旋转门限拒绝，因为先验已陈旧到没有意义）。也就是说：即便解算数学完美，也救不了这些帧。

平面先验版的无历史尝试：coverage 88.4%，但 t_err 中位 **644mm**、旋转中位 74° —— 两点 + 弱平面法向先验是**欠定**的（绕两点连线的滚转没有约束，重投影仍可为 0），优化器会停在初值附近给出「零重投影但错」的位姿。这种「自信的错位姿」比不给结果更糟，因此**不启用**。

**结论**：2 点方案能工作（crosscolor/room 覆盖 88–93%、3.6–21mm），但最需要的 hardmix/occlude_hand 被两件事卡死：① 部分遮挡时前端看不到那两个「可见」点（检测误差中位 240–325px）；② 先验不存在（occlude_hand 无任何三点全可见帧）或陈旧（中位 15.5 帧）。所以下一轮的方向不应再是位姿数学，而是**遮挡感知的前端**（半遮挡光斑/边缘环带）与**无先验自举**（尺度/平面约束 + 位姿级一致性门控），或者承认「手完全盖住」这类帧在纯视觉下不可测。

### 4.6 候选形状/匹配滤波与圆度奖励：三个负结果 + 前端/选点误差拆分（round 9）

**误差拆分（phone_far，6 序列、525 个三点全可见帧）**：det@10 all 0.627，其中

- **前端漏检 16.0%**：三色里至少有一色在候选列表（top-12）里找不到距 GT ≤10px 的点；
- **选点错误 21.3%**：三个候选都在 GT ≤10px 内，但三元组选择选错（通常是彩色干扰块拼出的「合理三角形」）；
- 其余为成功。

这条拆分把上一轮的「候选质量/选点」结论量化了：在退化域，**选点错误（21%）比前端漏检（16%）更大**。但本轮针对这两条做了三次改动，全部是负结果——说明这两个数字不是靠局部启发式能压下去的。

**负结果 1：形状无关的匹配滤波（MF）候选**（`frontend="union_mf"`，高斯/圆盘匹配滤波 + 局部极大，专治「半遮挡点被连通域形状过滤丢掉」）：

- 半遮挡点（GT `vis==1`）候选召回：`occlude_hand` 0.139 → **0.156**（+0.017），`hardmix` 0.039 → 0.038（不变）；
- phone_far 检测：小点桶（40–80px）0.292 → **0.046**，80+ 桶 0.705 → **0.533**。

原因：MF 在退化/低 SNR 图像上会把噪声与干扰块也拉成「峰」，候选列表被挤占；而真点在半遮挡时颜色证据中位只有 4/255（`occlude_hand`：GT 处颜色差 `r−max(g,b)` 中位 4.0，仅 42% 的点 >12），它不是「形状被过滤」而是**物理上颜色就没了**。这条也解释了为什么遮挡帧救不回来。

**负结果 2：三元组打分里奖励圆度**（`circ_w`，LED 点是圆盘、干扰块是矩形）：

| 配置 | circ_w=0 | 0.4 | 0.8 |
| --- | --- | --- | --- |
| phone_far | 0.6556 | 0.6204 | 0.6259 |
| clean | 0.7500 | 0.7111 | 0.7111 |

原因：圆度在 2–4px 的小点上就是噪声（一个 2×3 的连通域形状完全不能说明是圆是方），把它加权进代价只是把真点压下去。

**负结果 3（前一轮已记）**：候选级时序剪枝（§4.4）同样有害。

**结论与建议**：在「绝对阈值 → 对比度 → 尺度自适应 → 颜色解耦 → 亚像素」这条经典 CV 路线上，A–E 的收益已经拿到（clean 0.75、phone_far 0.656、小点桶 0.292；采集侧 4:4:4 时 0.794）；剩下 16% 前端 + 21% 选点的缺口**不是再加一条启发式能补的**，它需要一个能判别「彩色矩形干扰块 vs 小圆点」的表观模型，也就是回到学习型检测器（用真实/退化数据训练一个专用小检测器，输入就是这三色差图 + 低分辨率特征），或者等真机数据进来重标阈值。经典 CV 在这里的角色应是**保底 + 可解释 + 低延迟**（当前 v3 在 CPU 上 78–151 ms/帧，端侧可用）。

### 4.7 小检测器：候选级「圆点 vs 干扰块」分类器（round 10，首个正结果）

§4.6 把 phone_far 的误差拆成 **前端漏检 16% / 选点错误 21%**，并指出「再加局部启发式压不下去」。这一轮换成**学习一个 23.6k 参数的小分类器**，只做一件事：判断一个候选是不是真正的 LED 圆点（而不是彩色干扰块）。

**数据**：`research/scripts/build_dot_dataset.py` 用现有 v3 前端在 `train,hard_train`（40 序列 / 2180 帧）上抽候选，每个候选取该色差图的 15×15 patch；标签 = 距对应 GT 点 ≤4px 为正、≥12px 为负、中间灰区丢弃；每条序列随机叠一档退化（clean / phone_easy / phone_far / phone_harsh）。得到 **12,927 patch（3,862 正/9,065 负）**。

**模型**：1 通道 15×15 → Conv16-BN-ReLU-Pool → Conv32 → Conv64 → GAP → Linear，**23,585 参数**；AdamW 10 epoch（CPU 6 s），val_acc **0.896**、val_loss 0.246。推理 36 个候选/帧 **1.38 ms**（CPU）。

**接入**：`ClassicV3Detector(dot_cls_path=..., dot_cls_w=0.5)` 在候选层做 `score = (1-w)·classic_score + w·P(dot)`，不设硬阈值（`dot_cls_floor` 默认 0；试过 0.15，掉到 0.437）。复现：`far_bench --dot-cls research/results/dot_cls/dot_cls.pt`。

**结果（hard_test，未参与训练）**

| 配置 | classic2 | v3 union | v3 union + dot-cls |
| --- | --- | --- | --- |
| clean，6 序列 | — | 0.7500 | **0.8056** |
| phone_far，6 序列 | — | 0.6556 | **0.7352**（w=0.7；w=0.5 为 0.7333） |
| phone_far，12 序列 总 | 0.3398 | 0.7769 | **0.8213** |
| └ 40–80px 小点桶 | 0.108 | **0.292** | 0.215 |
| └ 80+px 桶 | 0.355 | 0.808 | **0.860** |

这是 A–F 完成后第一个在退化域**同时不伤害 clean**的改进：整体 +4.4 pt（12 序列 phone_far）、clean +5.6 pt。但代价是**小点桶回退**（0.292 → 0.215）：1–2px 的远距点在 15×15 patch 里和噪声块几乎不可分，分类器会压低它们；而 80+px 桶（近中距）受益最大。权重扫描（6 序列 phone_far）w=0.3/0.5/0.7 → 0.7315/0.7333/0.7352，对 w 不敏感。

### 4.7.1 尺度归一化 patch（round 11：修回小点桶）

§4.7 的固定 15×15 patch 在 1–2px 小点上内容几乎全是噪声，导致 40–80px 桶回退。修法：**取 patch 的窗口按「预计视半径」缩放**——`r_exp = 0.09·edge_px`（由上一帧位姿的视边长给出），窗口 = `15·clip(r_exp/3, 0.45, 2.5)` 原始像素，再 resize 回 15×15。训练集用同一规则重建（`dataset_scaled.npz`，同样 12,927 样本 / 3,862 正），重训得到 `dot_cls_scaled.pt`：**val_acc 0.926**（原 0.896）、val_loss 0.188。

| 配置 | baseline | 固定 patch | **尺度归一化 patch** |
| --- | --- | --- | --- |
| clean，6 序列 | 0.7500 | 0.8056 | **0.8463** |
| phone_far，6 序列 | 0.6556 | 0.7333 | **0.7593** |
| phone_far，12 序列 总 | 0.7769 | 0.8213 | **0.8380** |
| └ 40–80px 小点桶 | 0.292 | 0.215 | **0.369** |
| └ 80+px 桶 | 0.808 | 0.860 | **0.868** |

小点桶从 0.292 提到 0.369（+7.7pt，固定 patch 曾掉到 0.215），大桶也再涨 0.8pt——**尺度归一化同时修回了回退并扩大了收益**。整个退化域相对 A–F 完成时（v3 union 0.7769）累计 +6.1pt，相对最初 classic2（0.3398）是 2.46×。

复现：`far_bench ... --dot-cls research/results/dot_cls/dot_cls_scaled.pt --dot-cls-scale`；manifest 见 `research/results/dot_cls/manifest_scaled.json`。

**下一步（§4.7.1 已修）**：① ~~按预计视半径归一化 patch~~（已完成）；（小点先放大到统一尺度再进分类器）以救回小点桶；② 导出 ONNX（1.4 ms/36 候选，端侧可承受）并接进 App（App 无 torch；ONNX Runtime Android 依赖需联网，下一轮处理）；③ 用真实标注数据微调。

### 4.8 端侧落地：导出手写前向（round 12）

App 的 Gradle 缓存离线、没有 torch，也没有 ONNX Runtime，所以没有走「加依赖」的路线，而是把 23.6k 参数的小网络**折叠 BN 后导出成裸 float32 权重**，在 Kotlin 里手写前向。三个文件构成端侧链路：

- `research/scripts/export_dot_cls.py`：`dot_cls_scaled.pt` → `dot_cls.bin`（90.3 KB，little-endian，按 c1w/c1b/c2w/c2b/c3w/c3b/fcw/fcb 顺序）+ `dot_cls.json`（偏移/形状元数据）+ `dot_cls.onnx`（opset 13，仅作参考）。
- `composeApp/src/androidMain/kotlin/org/example/tridotpnp/DotPatchClassifier.kt`：`DotPatchWeights`（读裸权重）、`DotPatchClassifier.score(patch)`（3×conv+ReLU+MaxPool+GAP+Linear+Sigmoid，输入 0–255 自行归一）、`DotPatchExtractor.scaled(...)`（与 Python `patch_from_map_scaled` 同窗口规则；下采样用面积平均、放大用双线性）、`DotClassifierAssets`（从 `assets/dot_cls/dot_cls.bin` 懒加载，失败静默退化为 null）。
- `FarSpotDetector.applyClassifier(...)`：远距辅助路径凑齐候选后，按色组用尺度归一化 patch 估概率，`score = 0.5·classic + 0.5·P(dot)`，再排序截断；`CameraFrameProcessing.processImage` 每帧把 assets 分类器挂到 detector 上（null 时行为与旧版完全一致）。

**数值一致性**：40 条真实候选 patch 固件（20 正 / 20 负，TSV 从 `dataset_scaled.npz` 抽）上，Kotlin 前向与 PyTorch 参考概率最大偏差 **< 2e-3**（float32 累加顺序差异），正样本平均概率显著高于负样本；`torch.onnx` 与 PyTorch 的最大偏差 1.2e-7。单测 `DotPatchClassifierTest` 4 个，Kotlin 全量 **25 个测试通过**（11 tracker + 9 far detector + 1 far fixtures + 4 dot classifier）。

**构建**：`:composeApp:testDebugUnitTest` 与 `:composeApp:assembleDebug` 通过；APK **68,842,505 B**，`assets/dot_cls/{dot_cls.bin,dot_cls.json,dot_cls.onnx}` 已打包，dex 内含 `DotPatchClassifier`(10)/`DotPatchExtractor`(2)/`DotClassifierAssets`(7)/`applyClassifier`(8)。

**局限**：①只有固件级数值一致性证据，**没有真机端到端 det/t_err 数字**（手机侧需要真实远距帧）；②Kotlin patch 提取与 OpenCV 的插值实现略有差异（面积平均/双线性 vs INTER_AREA/INTER_LINEAR），在 1–2px 小点上可能带来额外偏差；③分类器只在「远距辅助」路径启用（常规三色齐全时不介入），因此端侧增益的上界是 Python 侧远距辅助路径的增量（phone_far 12 序列 0.7769→0.8380），并非全管线重测。

### 4.9 真机数据的一键验收（round 13）

协议写在 `research/docs/real_device_protocol.md`，但「采集完怎么判」必须同样提前固定，否则看到数字后总会想把阈值松一格。新增 `research/scripts/real_eval_acceptance.py` 把这套判据变成代码：

- **scored 模式**（默认）：读 `splits.json["real_test"]` + `real/annotations/<seq>.json`，用 classic-v3 union（可叠加小检测器）跑三点检测与 PnP，按 GT 距离分桶 `1–5 m` / `5–8 m` / `≥8 m`，输出每桶 `n / det@10 / 距离相对误差中位 / t_err 中位与 p90 / 坏距离帧数 / PASS-FAIL`。
- **判定阈值（前置于数据）**：`1–5 m` det@10 ≥ 0.80、距离相对误差中位 ≤ 5%、t_err 中位 ≤ 30 mm；`5–8 m` det@10 ≥ 0.50 且**不允许出现「检出三点但距离错 >20%」的帧**；`≥8 m` 只记录不设门。「无数据」不算 PASS（`NO DATA`）。
- **detection-only 模式**（`--video <mp4>`）：还没有标注时的预检——统计三点检出率与帧间点漂移（中位/p95），足以先发现「FOV 错、镜头脏、AE 搜索」这类采集问题。
- `research/tests/test_real_acceptance.py` 6 个测试把这些阈值钉死（好采集全过、det 掉线必 FAIL、距离误差超限必 FAIL、5–8 m 出现坏距离帧必 FAIL、无数据不是 PASS、分桶边界）。

现成的唯一真实片段 `smoke_real_desk.mp4` 预检结果：60/60 帧检出三点、点漂移中位 **6.06 px**、p95 **75.6 px**（近景桌面 + 干扰块，不代表远距；仅证明工具链可跑通）。

### 4.11 遮挡帧的 2 点路线：三条都不可用（结论）

`hard_test` 里 GT 恰好 2 点可见的帧有 655 帧（`hardmix` 400、`occlude_hand` 134、`handheld` 63…），此前全部记失败。三条 2 点方案都试过，结论一致：**不是解算问题，是观测问题**。

| 方案 | 需要什么 | 覆盖率 | t_err 中位 | ≤50mm |
| --- | --- | --- | --- | --- |
| 无输出（旧管线） | — | 0 | — | — |
| `completion`（先验投影缺失点，再跑 3 点 PnP） | 新鲜先验 | 0.438 | 601 mm | — |
| 2 点 + 运动先验（static） | 新鲜先验 | 0.144 | 26.8 mm | 72% |
| 2 点 + 运动先验（velocity） | 两帧历史 | ~0 | — | — |
| 2 点 + 平面法向先验（**不需要先验**） | 无 | **0.873** | **550.9 mm** | 11% |
| oracle（GT 像素 + 先验，上界） | — | 0.162 | 20.6 mm | 91% |

读法：

- **运动先验**在「先验新鲜」的少数帧上精度是够的（26.8 mm、72% ≤50 mm），但覆盖率只有 14%，且集中在 `crosscolor`/`room`；到了 `hardmix` 只剩 10%、`occlude_hand` 为 **0**——因为这两类没有任何「三点全可见」帧可以启动跟踪，先验年龄中位 **15.5 帧**。
- **平面法向先验**绕开了先验依赖，覆盖率冲到 0.873，但 t_err 中位 550.9 mm、≤50 mm 只有 11%：两点的候选关联完全自由，随便两个干扰块都能解出一个「平面大致正对」的位姿——**高覆盖 + 高错误**，比没有输出更糟。
- oracle 上界也只有 16% 覆盖、90% 精度：即便给 GT 像素，靠陈旧先验也会被 25° 旋转门限拒掉；而 `occlude_hand` 的 134 帧里「可见」点本身在颜色图上几乎不存在（候选 within10px 召回 13.3%、GT 处颜色差中位 4.0，仅 42% 过阈值）。

→ 结论：**遮挡帧（尤其 `occlude_hand`）对这种单目 + 颜色阈值前端是观测上限**，不是算法没调好。把它当成「必须救」的指标会诱导错误优化（例如强行输出 550 mm 的位姿）。下一步要么换观测（多视角/结构光/更长的曝光积分），要么在指标里明确区分「可见性不足」与「算法失败」。

**端侧配套（round 14）**：`FarSpotDetector` 在**没有上一帧三点**（首帧/跟踪丢失）时，改用「本帧候选的中位等效半径」做尺度归一化（`FarSpot.area` 新增字段），不再退化到固定 15px 窗口；`FarSpotPriorFreeScaleTest` 用合成 2×2 点在 `expectedEdgePx=0` 下验证仍能凑齐三色（Kotlin 26 个测试通过）。

### 4.11b 端侧 C（亚像素）落地

远距小光斑的定位误差主要来自「整像素质心」：1–2 px 的点在 640 宽分析图上，
整像素量化就是 0.5 px 量级。端侧 `FarSpotDetector` 对「外接框 ≤3.5 px」的候选增加
**逐轴抛物线插值**（`refineSubpixel`：3×3 邻域、分母过小跳过、位移夹在 ±0.5 px），
与 Python 侧 4× 上采样质心等价但便宜（无额外拷贝）。新增 3 个 JVM 测试：
分数中心恢复 <0.35 px、平坦图不位移、病态图案位移被夹住；Kotlin 单测总数 29。

### 4.11c C（ROI 上采样）触发率与真实收益

上一节的端侧抛物线细化只对「外接框 ≤3.5 px」生效。回查实际触发率：
hard_test 命中候选的连通域面积中位 **400 px（clean）/367.5 px（phone_far）**，
`area ≤ 3` 占比 **0.000** —— 也就是说历史上 `roi_upsample=True` 的 v3 数字里，
4× 上采样分支**从未触发过**，精度实际来自窗口质心 `_subpixel`。

把 C 改成「对每个候选峰值窗口都做 4× 上采样质心」（`upsample_mode="all"`）再 A/B
（hard_test 6 序列、匹配到的候选点像素误差，n 为匹配点数中位数口径）：

| 配置 | tiny（历史行为） | all（宽触发） | off |
| --- | --- | --- | --- |
| clean 中位 / 均值 | 1.0085 / 1.2776 | **0.9241 / 1.1391** | 1.0085 / 1.2776 |
| phone_far 中位 / 均值 | **0.7863 / 1.0947** | 1.0358 / 1.2325 | — |

结论：**窄触发在当前工作点等价于 off（死代码）；宽触发在干净域 +0.08 px、在退化域 −0.25 px（变差）**。
退化帧的颜色响应有光晕/噪声，双三次上采样会把这些放大，而按 bbox 缩放的窗口质心更稳。
因此 C 保持「只对真正 1–2 px 的点启用」，端侧抛物线同理（±0.5 px 夹紧、只对 ≤3.5 px 外接框）。

### 4.11d 主线三点自洽性校验（端侧，round 19）

远距辅助原先只在「凑不齐三点」时触发；但真实帧里更常见的是**凑齐三个错误点**：
`BrightSpotDetector` 被泛光/干扰块骗到，垂心三角形在几何上荒谬却照样进 PnP，
这类帧远距辅助永远不会被调用。

端侧新增 `TripleConsistency.isPlausible(points, expectedEdgePx, tolerance=0.45)`：

- 三点平均边长 ≥6 px；
- 边长相对离散度 `(max−min)/mean ≤ 0.5`（排除共线/压扁）；
- 有上一帧先验时，平均边长须落在 `expectedEdgePx × [0.55, 1.45]`。

`processImage` 里改为：`mainTriplePlausible = size==3 && isPlausible(...)`；
只有 `!mainTriplePlausible` 才走远距辅助。这样「凑齐但错」的帧也会被重找一次。

代价与风险：不自洽帧会多付一次远距检测（约 50–80 ms，且仅在失败/可疑帧）；
若真机快速接近导致视边长变化 >45% 会误触发，属于可接受退化（结果只是多花一次检测）。

新增 6 个 JVM 测试（等边通过、共线拒绝、尺度不符拒绝、<6px 拒绝、压扁拒绝、非三点拒绝）；
Kotlin 单测总数 **35**；APK 68,847,561 B，dex 含 `TripleConsistency` 2 次。

**激活率与收益（Python 复现 app 主路径 B1，hard_test 前 6 序列、三点全可见帧）**：

| 指标 | 值 |
| --- | --- |
| B1 给出三点的帧 | 522/540 |
| 其中几何不自洽 | **169（32.4%）** 被门拦下 |
| det@10 all：B1 原始 | 0.221 |
| det@10 all：门控后（不自洽改用 classic3 union + dot-cls） | **0.4476** |

读法：app 主路径在 realistic 域上「凑齐三点」里有三分之一几何是错的，这些帧现在会被重找；
上表用 GT 深度换算的 expectedEdge（比端侧「上一帧预测」更乐观），因此 0.4476 是**上界**，
端侧实际收益取决于跟踪先验质量。复现脚本：`research/scripts/triple_gate_ab.py`。

### 4.11e 自洽门：真实先验 vs GT 上界（round 20）

上表的 `expectedEdgePx` 用的是 GT 深度换算，端侧实际只有「上一帧已接受结果的视边长」。
用 `research/scripts/triple_gate_tracker_ab.py` 模拟真实链路（B1 主路径 → 自洽门 →

| phone_far | 0.2076 | 0.3886 | **0.3790** | 192 / 525 | 108 |

### 4.18 前端分辨率旋钮：精度-成本曲线（round 27）

§4.17 的结论是「跳帧不可行」，那就只剩「让单帧更便宜」。对比度前端最主要的成本随像素数走，

| 512 | 0.583（−1.7 pt） | 0.577（−3.2 pt） | 2.10 px | 64% |
| 448 | 0.547（−5.3 pt） | — | — | 49% |

### 4.16 phone_harsh 的瓶颈在采集侧（round 24）

round 23 看到 `phone_harsh` 一档明显落后（fal-primary det 0.52、pose coverage 0.81），本轮用同一帧集
（hard_test 前 6 序列、540 帧、phone_harsh 退化）做「采集开关 × 前端」交叉对照，分类器仍是 `dot_cls_scaled.pt`：

| --- | --- | --- | --- |

结论：

1. **harsh 档的损失主要来自采集侧**（色度 4:2:0 把 1–2 px 彩点平均掉 ≈ +17 pt；分辨率再 ≈ +3 pt），
   前端与分类器只能部分补偿；这与 §4.2/§4.3 的归因一致，但第一次在「最难档 + 端到端链路」上量化。
2. **加强降噪（ISP NR）不是解药**：单开 0.35 无收益（v3 0.600→0.596），与 4:4:4 叠加反而 −4 pt（0.804→0.761）——
   降噪把本来就微弱的小点抹平，这与 §4.2 的结论「保留适度降噪、别为了干净而关掉色度」互相印证后更新为
   「优先保色度与分辨率，降噪只需默认适度」。
3. 端到端 harsh 的上限因此是「采集 + 前端」之和：本轮把 harsh 从 0.52 拉到 0.65、coverage 0.81→0.90；
   剩余差距需要真机数据判断（合成 harsh 是四档叠加的极端值，真机 ISP 的实际行为只有采集后才可量）。

### 4.12 评测口径：det@10 的第三种分母（observable）

遮挡类 factor 一直有两个都不诚实的口径：`det10_legacy` 把 `vis<2` 的帧全丢掉（`hardmix` 只剩 162/720 帧），`det10_all` 把 `vis==0`（点根本不在画里）的帧记成算法失败。本轮在 `metrics.py` 增加 `det10_observable`：

- **分母** = 三个 GT 点都至少「存在」的帧（`vis >= 1`）；
- **分子** = 该帧三点预测都在 10 px 内。

这样把「物理不可观测」从算法错误里剥出来，又不至于像 legacy 那样只挑最有利的帧。已接入 `metrics.summarize()` 与 `eval_v2` 的 summary/report。

**hard_test（8 序列 / 720 帧，clean）**

| 方法 | det@10 all | legacy | observable | n_observable |
| --- | --- | --- | --- | --- |
| b0 | 0.1444 | 0.1475 | 0.1475 | 705 |
| classic2 | 0.7903 | 0.8071 | 0.8071 | 705 |
| classic3 (union) | 0.7736 | 0.7901 | 0.7901 | 705 |
| classic3 + dot-cls | **0.8486** | **0.8667** | **0.8667** | 705 |

**hardmix + occlude_hand（8 序列 / 720 帧）**

| 方法 | det@10 all | legacy | observable | n_observable |
| --- | --- | --- | --- | --- |
| b0 | 0.0000 | 0.0000 | 0.0000 | 660 |
| classic2 | 0.0264 | 0.1173 | 0.0394 | 660 |
| classic3 (union) | 0.0014 | 0.0062 | 0.0015 | 660 |
| classic3 + dot-cls | 0.0375 | **0.1667** | 0.0561 | 660 |

三条读法：

1. 在 clean 的 8 序列上三种分母几乎一致（没有 `vis<2` 的帧），说明这套子集本身不遮挡；真正的差异只在 hardmix/occlude_hand。
2. 在 hardmix/occlude_hand 上，legacy 的 0.1667 与 observable 的 0.0561 差 3 倍：**旧报告里「0.88」这类数字正是靠 legacy 分母撑起来的**；补上部分可见帧后，成功率掉到 4–6%。
3. observable 仍然很低（≤0.06），说明即使只算「点还在」的帧，前端也没法稳定定位它们——这和第 4.11 节的 oracle 结论一致：**瓶颈在前端观测，不在 3 点/2 点解算**。

顺带得到一个正结果：clean 的 8 序列上 `classic3 + dot-cls` 0.7736 → **0.8486**（+7.5pt，legacy 0.7901 → 0.8667）——分类器即使在干净数据上也有效，是目前 clean 域单项最大提升。

## 5. 真实视频（无标注）上的内容级验证

现有唯一真实视频 `datasets/TriDotPose/real/videos/smoke_real_desk.mp4`（60 帧，桌面近景、含干扰块）。它没有标注，但可以回答两件事：真实内容与哪档退化最像；退化后前端是否还锁在正确的点上。

| 场景 | mean V | 灰度 σ | Laplacian 方差 | 色差 p99.5 |
| --- | --- | --- | --- | --- |
| 真实视频 `smoke_real_desk.mp4` | 68.14 | 8.92 | 187.65 | 52.8 |
| 合成 clean（同长度） | 61.57 | 11.08 | 68.24 | 21.87 |

| 退化档 | 方法 | 检出三点 | 点漂移中位 (px) | 视边长误差中位 (px) |
| --- | --- | --- | --- | --- |
| 原始 | classic2 | 60/60 | 0.07 | 0.92 |
| 原始 | classic3 | 60/60 | 0.00 | 0.00 |
| phone_easy | classic2 | 60/60 | 317.89 | 321.53 |
| phone_easy | classic3 | 60/60 | 0.37 | 0.61 |
| phone_far | classic2 | 60/60 | 277.13 | 300.14 |
| phone_far | classic3 | 60/60 | 0.89 | 0.61 |
| phone_harsh | classic2 | 60/60 | 260.38 | 262.20 |
| phone_harsh | classic3 | 60/60 | 1.08 | 0.68 |

> 参考帧 = classic3 在未退化真实帧上的三点（其自身视边长 152px，60/60 帧一致）。点漂移 = 与参考帧同色点的像素距离中位。

结论：真实视频的色差 p99.5 是合成 clean 的 2.4 倍、Laplacian 方差 2.7 倍（桌面木纹 + 干扰块），并不像电话远距场景。把它当作「真实内容」的替身加上三档退化后：classic2 在 60/60 帧仍然「检出三点」，但点漂移中位 260–318px（锁到干扰块上了，视边长从 152px 变成 414–473px，是一个完整的**假三角形**）；v3 同条件下点漂移 0.37–1.08px、视边长误差 <0.7px。说明在真实图像内容上，绝对阈值前端遇到曝光/噪声变化会整体漂移，而对比度前端不会。

## 6. 局限与后续

1. **不是真机**：退化模型仍是仿真的，假设零畸变、无卷帘、无镜头脏污；真机 1–8m 距离扫描才能定论。
2. **单用对比度会掉 clean**：纯对比度前端在 clean 上是 0.783（v2 0.815）；并集模式（对比度 ∪ v2 绝对阈值）回到 0.824，说明两者互补而不是替代。注意 B0 在 phone_far 上 0.426 反而高于 classic2 的 0.340 —— 更「笨」的固定 HSV 阈值在退化下比调过的 v2 更稳。
3. **screen 是可见性边界，不是选点问题**：`screen` 帧在 640 宽下 GT 处颜色差只有 5–16（阈值 12）、HS(V) 饱和度 22–51（周围环带 68–217）、luma 顶帽在个别帧只有 30。同一帧换 640/960/1280 三档分析宽度都选错（点误差 56–390px），**加分辨率救不回来**；端侧能做的只有 E 的「提高分析分辨率 + 关 ISP 降噪 + 锁 AWB」，或真机在屏幕类场景下调曝光/避免屏保反光。
4. **颜色完全不可得时的可行性（Python 单帧探测）**：luma 顶帽候选 + 6 种颜色排列 × PnP 位姿连续性 → `far` 1.1/1.1/1.2px、`handheld` 0.9/0.8/0.9px（**零颜色也能定位**）；`clutter`/`screen` 无位姿一致三元组（clutter 真点在候选里但排名 >12，screen 缺点）。说明「检测-颜色解耦」可按此路线做失败帧兜底，代价约 200–400 次 P3P/帧，只在 `refinedSpots.size != 3` 时用。
5. **延迟**：Python 全分辨率 v3 约 78ms/帧（对比度）/151ms/帧（并集），手机 AArch64 单核会更慢；真机建议 2–3 级金字塔 + 预测 ROI。
6. **遮挡帧（round 8 已实测）**：2 点 + 已知几何解算数学可行（GT 像素上 t_err 中位 20.6mm），但在 hard_test 的 655 个「恰两点可见」帧上实际覆盖只有 13.6%（t 中位 220.6mm）；hardmix/occlude_hand 被前端遮挡漏检（检测误差中位 325px）与先验陈旧/缺失（occlude_hand 0 可用先验）卡死。无先验的平面法向版欠定（t 中位 644mm），不可用。
7. **固件数量**：真实帧固件目前只有 4 factor × 2 preset = 8 张、各 1 帧；结论强度有限，后续应扩到每个 factor 5–10 帧并加 `handheld/clutter` 的多帧序列。
8. **时序门控的负结果**：候选级 prune（`prior_gate`）在四配置上掉 0.01–0.05，dual 模式持平；`_score_triple` 的软时序项已经覆盖了这部分信息。端侧因此保留「门限只加速、不否决」的两遍搜索语义。
9. **阈值自适应的负结果**：`threshold_mode ∈ {tile, tile_rel, snr}` 在本评测上没有任何收益（tile 与 percentile 逐帧相同，snr 明显更差）；实测有效阈值在四配置下都停在常数底 12。这说明 v3 在退化帧上的实际判据仍是「绝对对比度 > 12」，真正限制它的是候选质量/选点而不是阈值。若要继续压远距，应改进 **候选去噪（时序/几何一致性）与选点**，而不是继续调阈值。
